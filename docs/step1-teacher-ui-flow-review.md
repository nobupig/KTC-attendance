## 2. 現状UI導線の整理

### 2.1 画面構成

デスクトップ幅では、左360pxの「担当授業」パネルと、右側の「出席入力」パネルが2列で表示される。900px以下では1列になり、担当授業パネルの下に出席入力パネルが並ぶ。

表示順は次のとおりである。

```text
ページヘッダー
└─ メッセージ領域

担当授業パネル
├─ 過去未保存サマリー
│  └─ 展開時: 過去未保存詳細（最大50件）
├─ 本日の授業 / 過去授業を検索 タブ
├─ 過去日付検索（過去モードのみ）
├─ 時限ごとの選択
└─ 授業一覧と操作ボタン

出席入力パネル
├─ 選択授業情報
├─ 最終保存情報
├─ 班選択（工学実験のみ）
├─ 上部操作・保存ボタン
├─ 保存状態と出欠集計
├─ 学生一覧・状態ボタン・任意の欠席リスク表示
└─ 下部保存ボタン
```

### 2.2 初期表示の実処理順

`init()`は本日の授業一覧を先に読み込む。通常表示では授業を自動選択せず、一覧の各操作ボタンから教員に次の操作を選ばせる。

未保存サマリーは、本日の授業一覧読み込み開始から7秒後に`loadTeacherUnsavedSummary()`を呼び、さらに800ms後にFast APIを呼ぶ。したがって通常時は約7.8秒後から未保存件数が更新される。

```text
画面を開く
├─ 即時: ボタンイベント設定、管理者用なりすまし状態取得
├─ 即時: 本日の授業一覧を読み込む
│  ├─ 授業一覧を表示
│  └─ 保存状態を後読みして「確認中...」を更新
├─ 授業は自動選択しない
└─ 7秒後
   └─ さらに800ms後
      └─ Fast APIで過去未保存サマリーを表示
```

本日の授業を優先している点は妥当である。一方、未保存サマリーは担当授業パネルの最上部にあるため、読み込み後や詳細展開後は、過去対応が本日の授業より視覚的に上位になる。

### 2.3 授業一覧と保存状態

通常授業には次の2操作が表示される。

- `欠席者なしで保存`
- `欠席者を入力`

工学実験など班選択が必要な授業は、`班を選択して入力`だけを表示する。

保存状態は通常授業で`確認中...`、`保存済み`、`未保存`、過去モードでは`開くと確認`を使う。工学実験では複数の関連クラスをまとめ、`一部確認中`、`全保存済み`、`一部保存済み`、`未保存`を使う。

保存状態は授業一覧の読み込み後に別リクエストで後読みされる。その間も操作ボタンは表示されるため、教員は保存済み状態が確定する前に操作できる。

### 2.4 授業カード実装上の確認事項

コードには`.class-card`、`.class-card-top`、`.period-badge`、`.class-card.active`のCSSがあり、`renderClassList()`でも`activeClass`を計算している。しかし現在の生成HTMLでは、カード開始要素、カード上部開始要素、時限バッジの出力が確認できず、状態ラベルの直後に閉じ要素が出力されている。

このため、次の可能性がある。

- 授業カードの枠、余白、hover、選択中表示が意図どおり適用されていない
- カード内に時限が直接表示されず、2コマ連続授業を見分けにくい
- 不完全なHTMLをブラウザが補正して表示しており、ブラウザ差が出る
- `activeClass`と`isSaved`の一部が実質的に使われていない

Step1-Aでは修正しない。Step1-B開始前に、実画面のDOMとスクリーンショットで事実確認し、再現した場合は最優先の小規模修正とする。

### 2.5 出席入力エリア

通常授業で`欠席者を入力`を押すと、学生一覧と保存済み出欠を読み込む。初期状態は全員出席で、各学生に`出席`、`欠席`、`遅刻`、`公欠`のボタンが並ぶ。

- 状態ボタンを押すと即座に集計を更新し、`未保存の変更があります`と表示する
- 保存ボタンは一覧の上部と下部にある
- `全員を出席にする`で全員を出席へ戻せる
- 欠席リスクは任意の追加読み込みであり、通常入力を妨げない
- 保存済みデータを開いた場合も保存ボタンは利用できる

授業未選択時は、右パネルに「どの操作を選ぶか」の説明が出る。デスクトップでは見やすいが、1列表示では授業一覧の下にあるため、最初の説明が画面外になりやすい。

### 2.6 過去未保存導線

Fastサマリーが`ready`かつ1件以上の場合、件数、対象期間、最終確認時刻と`詳細を見る`を表示する。詳細は先頭50件だけで、各行に`この授業を開く`がある。

`この授業を開く`を押すと、過去モードへの切り替え、日付設定、該当日の授業検索、対象授業選択、名簿読み込みまでを自動で行う。この部分は、手動の日付検索より短い有効な導線である。

保存成功後は、未保存詳細から該当項目を除き、サマリー件数をローカルで1件減らす。ただし、画面は過去授業の出席入力位置に残り、次の行動を示す専用ボタンはない。

### 2.7 現状フロー図

```text
日常の本日授業

画面を開く
  ↓
本日の授業一覧を確認
  ├─ 欠席者なし → カードの専用ボタン → 確認ダイアログ → 保存完了
  └─ 欠席者あり → 名簿を開く → 学生ごとに状態指定 → 保存完了


過去未保存対応

未保存サマリーを待つ
  ↓
「詳細を見る」
  ↓
最大50件の一覧から「この授業を開く」
  ↓
過去モード・日付検索・授業選択を自動実行
  ↓
名簿で確認・修正して保存
  ↓
件数は1件減るが、次の未保存 / 一覧へ戻る / 本日へ戻る案内はない
```

### 2.8 改善後に目指すフロー

Step1で目指すのは、APIやDBを変えず、画面上の優先順位と次の操作を明確にすることである。

```text
画面を開く
  ↓
「今日やること」を最上位で確認
  ├─ 未保存・要入力の授業 → 主操作を1つ選ぶ → 保存
  └─ 保存済み授業 → 必要な場合だけ修正を開く
  ↓
保存結果と「次にすること」を同じ場所で確認

過去未保存は第二導線
  ↓
コンパクトな件数表示
  ↓ 必要なときだけ
一覧を開く → 対象授業を処理 → 次の未保存 / 一覧へ戻る / 本日へ戻る
```

## 3. 利用シナリオ別の操作フロー

クリック数は、授業一覧が表示された後の標準操作を数える。待ち時間、スクロール、確認のための視線移動は含めない。学生の状態変更は対象学生1人につき1操作として数える。

### 3.1 欠席者なしの日

#### 現状

通常授業1件を初めて保存する最短導線は2操作である。

1. 授業の`欠席者なしで保存`を押す
2. 上書き注意を含む確認ダイアログでOKを押す

名簿を開かず保存できるため、基本導線は短い。一方、未保存の新規授業でも、保存済み授業を全員出席で上書きする場合と同じ長い確認文が出る。保存状態がまだ`確認中...`でもボタンを押せる。

#### 改善候補

- 状態確定後に主操作を明確にする
- 新規未保存と保存済み上書きで確認の強さを分ける
- 新規未保存は誤操作対策を残しつつ、1操作保存の可否を検討する
- 保存完了後に、カード自体で完了状態と次の授業を確認できるようにする

### 3.2 欠席者ありの日

#### 現状

欠席者1人の場合の最短導線は3操作である。

1. `欠席者を入力`を押す
2. 対象学生の`欠席`、`遅刻`、または`公欠`を押す
3. 上部または下部の`保存する`を押す

欠席者が複数なら、状態指定の回数だけ操作が増える。学生一覧は初期状態が全員出席であり、例外だけを指定する方式は合理的である。

課題は、授業一覧と入力エリアが別パネルであること、スマートフォンでは入力エリアが一覧の下にあること、保存後に元の授業カードへ視線を戻さないと一覧全体の進捗が分かりにくいことである。

#### 改善候補

- 授業選択後に入力エリアへフォーカスまたはスクロールする
- 選択中授業の時限、クラス、保存状態を入力エリア上部で強調する
- 保存後は同じ位置に成功状態と次の候補を表示する
- 状態ボタンのタップ領域と選択状態をスマートフォンで再確認する

### 3.3 過去未保存授業を処理する日

#### 現状

未保存詳細が閉じている状態から、欠席者なしの過去授業を名簿経由で保存する最短導線は3操作である。

1. `詳細を見る`を押す
2. 対象行の`この授業を開く`を押す
3. 自動表示された名簿を確認して`保存する`を押す

欠席者がいれば、3の前に対象学生の状態を指定する。手動検索の場合は、過去タブ、日付選択、検索、授業操作が必要になるため、未保存一覧からの導線の方が短い。

保存後は件数と開いている詳細一覧が更新されるが、次の未保存を続けるための`次へ`、詳細位置へ戻るためのフォーカス、本日の授業へ戻るための案内はない。処理対象が多い場合、上部の一覧と下部の入力エリアを往復する。

詳細は先頭50件までで、51件目以降を同じ一覧から開く手段がない。T018のように77件ある場合、残り27件は注記されるだけで、日付を手動検索する必要がある。

#### 改善候補

- Fast APIの既存`offset`を使い、API仕様を変えずに追加50件を取得する
- 保存後に`次の未保存を開く`、`未保存一覧へ戻る`、`本日の授業へ戻る`を表示する
- 一覧内で処理済み件数と残件数を明示する
- 詳細展開で本日の授業一覧を下へ押し下げすぎない構造を検討する

### 3.4 工学実験・班選択あり授業

#### 現状

班内が全員出席の場合でも、標準的には3操作必要である。

1. `班を選択して入力`を押す
2. 班を選択する
3. 名簿を確認して`保存する`を押す

欠席者がいれば状態指定が追加される。別の班を続けて処理する場合は、班選択と保存を繰り返す。

工学実験は同一日・時限・科目の関連クラスを1つの一覧項目へまとめ、`全保存済み`、`一部保存済み`などを表示する。ただし、どの班が保存済みで、どの班が未保存かはカードだけでは分からない。班選択後に初めて対象名簿と保存状態が明確になる。

#### 改善候補

- 班ごとの完了状態を班選択肢または補助表示で示す
- `一部保存済み`を「何班中何班」のように具体化できるか、既存データで検討する
- 選択中の班を入力エリアと授業一覧の双方で強調する
- Step1では班単位の既存保存を維持し、全班一括保存は行わない

### 3.5 2コマ連続授業

#### 現状

セッションは時限ごとに別キーで管理され、各コマを個別に保存する。時限ごとのクイック選択はあるが、1コマ目の保存後に2コマ目を案内したり、連続コマをまとめて保存したりはしない。

欠席者なしなら、2コマで`欠席者なしで保存`と確認OKをそれぞれ行うため、最短4操作となる。欠席者入力では名簿読み込み、状態指定、保存を各コマで繰り返す。

さらに、授業カード生成HTMLで時限バッジが出力されていない可能性があり、同一科目・同一クラスの連続コマをカード上で判別しにくいリスクがある。

#### 改善候補

- Step1-Bでカード上の時限表示を必須にする
- 保存後に同一科目・次時限の授業を候補として示す
- Step1では個別保存を維持し、完全統合保存は次StepのAPI設計へ送る

### 3.6 スマートフォン・狭い画面での利用

#### 現状

- 900px以下で担当授業と出席入力が縦積みになる
- 授業を選んでも入力エリアへの自動スクロールはない
- 未保存詳細を展開すると、最大50件が本日の授業一覧より前に並ぶ
- 720px以下では未保存詳細行とボタンが縦並びになる
- 768px以下では保存ボタンが全幅になり、上部・下部の両方にある
- 学生一覧は横スクロール可能だが、欠席リスク表示時は列が大きく増える
- 状態ボタンは折り返せるが、学生ごとの行高が増えやすい
- 授業カードの操作ボタンはスマートフォン用の全幅指定がない

#### 改善候補

- 授業選択後と保存後のスクロール・フォーカスを設計する
- 本日の作業を未保存詳細より先に保つ
- 授業カードの主操作を全幅または十分なタップ領域にする
- 欠席リスク列は必要時だけ表示する現状を維持し、狭い画面では要約表示も検討する
- 360px前後の実機相当幅で、横スクロール、固定ヘッダー、ボタン折り返しを確認する

## 5. 改善優先度

### 優先度0: 表示構造と判断の安全性

1. 授業カードDOM、時限表示、選択中表示を実画面で確認し、必要なら修正する
2. `保存済み`、`未保存`、`確認中`を直感的に区別する
3. 保存状態確認中の上書きリスクを抑える
4. Step0の本番反映とStep1 UI変更を別リリースにする

### 優先度1: 毎日の最短導線

1. 本日の授業カードを最優先に見せる
2. 欠席者なし、欠席者ありの主操作を迷わず選べるようにする
3. 保存完了をカードと入力エリアの両方で認識できるようにする
4. スマートフォンで授業選択後の入力位置へ到達しやすくする

### 優先度2: 過去未保存の連続処理

## 9. リスクと注意点

### Step0との分離

Step0は本番未反映である。Step1-B以降を同じ本番反映単位へ追加すると、性能改善、キャッシュ運用、UI変更の問題を切り分けにくくなる。原則として、Step0を独立して反映・安定確認した後、別ブランチ・別デプロイでStep1へ進む。

並行して設計や試作をする場合も、Step0のリリースコミットを固定し、Step1の変更を別ブランチへ分離する。

### 保存安全性

- `欠席者なしで保存`は既存の欠席・遅刻・公欠を消す可能性がある
- クリック削減だけを目的に確認を外さない
- 保存状態確認中に操作を制限する場合、通信失敗時でも入力自体を完全に塞がない設計が必要
- 保存後ローカル減算は画面上の暫定同期であり、次回buildとの一致確認を維持する

### 状態の一貫性

- 授業カード、入力エリア、未保存サマリーの3か所で状態を同期する必要がある
- `未保存`は「当日の出席が未保存」と「過去未保存一覧」の両方で使われるため、文脈を明確にする
- キャッシュが非`ready`でも0件と表示しないStep0仕様を維持する

### レスポンシブ対応

- CSSだけでなく、選択後のスクロール位置とフォーカスを検証する
- 50件詳細、学生名簿、欠席リスク列は縦横とも長くなる
- iOS Safari、Android Chrome相当の幅で、button、select、確認ダイアログ後の位置を確認する

### 工学実験・2コマ連続

- 表示上まとめても保存単位は既存のclassId、date、period、groupを維持する
- 表示改善で異なるセッションを同一保存と誤認させない
- 工学実験のカード集約キーと、班選択・保存キーの違いを壊さない
